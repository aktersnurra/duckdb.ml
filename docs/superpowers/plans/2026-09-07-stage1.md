# Stage 1 compatibility and FFI Implementation Plan

> **For agentic workers:** Execute inline using the writing-plans and test-driven-development skills; the approved single-writer task forbids subagent dispatch. Check off only demonstrated results.

**Goal:** Reproducibly compile a project-local OxCaml toolchain, run both scheduler stacks and a minimal chunk/vector DuckDB query, and select an FFI from compiled comparative evidence.

**Architecture:** Private stage-1 probes, not public ownership APIs. Project-local opam root and switch isolate all dependency changes. A generated-stub probe and a handwritten-stub probe share query expectations; each retains native arguments before releasing the runtime lock.

**Tech Stack:** OxCaml 5.2.0+ox as currently recommended upstream; pinned OxCaml/default opam snapshots; Base, Dune, Async, Eio, Ctypes; DuckDB public C API on x86-64 glibc.

## Task 3: two FFI probes and minimal query

**Files (approved execution refinement):** under `stage1/ffi/`, paired `.mli`/`.ml` files `handwritten_probe`, `generated_probe`, `generated_bindings`, `generate_stubs`, `probe_error`, `ffi_tests`; `handwritten_stubs.c`, `native_probe.h`, `native_probe.c`, `native_diagnostics.c`, `ctypes_unboxed.mli.fail`, `check_unboxed.sh`, `dune`. `.clangd` points optional native diagnostics at an ignored local compilation database.

The supervisor approved sharing the native query/lifecycle helper between the two real FFI paths. This isolates marshalling, locking and accessor differences rather than duplicating DuckDB resource logic. It does not establish direct binding coverage or a future borrowed API.

**Private OCaml interface (write `.mli` first):**

```ocaml
(* Probe_error.mli *)
type t = Open_failed of string | Connect_failed | Query_failed of string
       | Unsupported_schema | Allocation_failed | Embedded_nul
(* Each private query wrapper's .mli *)
val query_int64 : string -> (int64 array, Probe_error.t) result
```

This is an owned-copy BIGINT-only experiment, not a public API. Unsupported schemas fail explicitly. Any additional schema failure uses a named `Unsupported_schema` variant before implementation.

- [x] Write assertions for `SELECT i::BIGINT FROM range(3) t(i)` returning `[|0L; 1L; 2L|]`, invalid SQL producing `Query_failed`, repeated invalid/valid cycles, empty result, and unsupported column type. Run for red.
- [x] Handwritten C copies SQL to native memory before entering a blocking section, opens/connects, calls `duckdb_query`, fetches using `duckdb_fetch_chunk`, `duckdb_data_chunk_get_vector`, `duckdb_vector_get_data` and validity APIs, copies foreign vector values to native storage while unlocked and subsequently to OCaml with the lock held, destroys chunks/results on success and error, disconnects then closes. No movable heap access while unlocked.
- [x] Ctypes-generated stubs use `Cstubs.write_c ~concurrency:Cstubs.unlocked` (validate installed signature), native-owned argument storage across unlocked calls, and the same public chunk/vector API. Inspect generated C for conversion-before-unlock and cleanup. Do not infer lock behavior from generator options alone.
- [x] Add a native slow-call test with a concurrent OCaml systhread heartbeat for each approach; require heartbeat while native work is in flight. Add C/OCaml accessor experiment for `int64#` if supported and boxed reference equivalence at signed 64-bit boundaries. Compile failures are evidence of unsupported syntax/representation, not a reason to claim support.
- [x] Run `stage1/run runtest`; run ASan/UBSan native diagnostics (Valgrind if present), exercising failed query cleanup repeatedly. Check DuckDB's public header destruction documentation for all failure paths.
- [x] Commit `test: compare DuckDB generated and handwritten stubs`; `jj new`.
